BRL-CAD portable database history, format 1.0
============================================

Draft for implementation and interoperability testing. An archive is a
self-contained store of immutable artifacts and a selected revision. A
portable DB5 file carries the archive together with the selected model.
The model remains a collection of ordinary DB5 application records.

Byte encoding and artifact identity
-----------------------------------

All integers are unsigned and big-endian unless marked i64, a signed
twos-complement integer. u8, u16 and u64 occupy one, two and eight
bytes. A `bytes` field is u64 length followed by exactly that many
bytes. Counts exclude the count field itself. Names are nonempty byte
strings without NUL. Order names lexicographically as unsigned bytes,
with a shorter prefix before any extension. Names are case-sensitive.
Labels and authors are byte strings without NUL. Writers should use
UTF-8 for display text. Empty author means unspecified. A time is i64
seconds since 1970-01-01 00:00:00 UTC.

An ID occupies 32 bytes. Its value is SHA-256 of the following bytes.
See https://csrc.nist.gov/pubs/fips/180-4/upd1/final for SHA-256.

    "BRLCAD-HISTORY"  u16(1)  u8(tag)  bytes(payload)

The domain string uses ASCII without a terminator. Tags are the ASCII
bytes `B`, `O`, `M` and `R` defined below. The all-zero ID represents
absence where permitted and cannot name an artifact. Hash the canonical
payload before any storage encoding. Database offsets, map or archive
placement, checkpoint names, preferred children and checkout state do
not contribute to artifact IDs. Hexadecimal display uses the 64 digits
in byte order. Reconstruct and verify artifacts without changing IDs
across archive export, reimport, compaction and workspace storage.

The archive container version, workspace schema version and artifact
encoding version are independent. Archive 1.0 selects artifact encoding
1. A new container or workspace can change indexes, compression or
delta storage and keep the same artifact IDs. A change to canonical
artifact bytes requires a new encoding
version. A reader interprets each retained ID under the original
encoding. A migration verifies the closure of retained references and
the selected model before publishing the new store.

Artifacts
---------

`B` stores the exact serialized DB5 body field without the field's
length prefix. Refer to a `B` only for a nonempty field. These bytes
remain opaque regardless of the primitive type or DB5 compression tag.

`O` stores one named DB5 application record split around its body.

    ID body  bytes prefix  bytes suffix

When a nonempty body is present, the prefix ends at the first body
byte, including the DB5 field length. The suffix starts immediately
after the body and includes original padding and trailing DB5 magic.
When there are no body bytes, use a zero body ID, put the complete
record in the prefix and make the suffix empty. This covers both an
absent body field and a present zero-length field. Concatenate prefix,
body and suffix to recover the exact record. Check the reconstruction
with a bounded DB5 parser. Require that the parser locates the split at
the encoded boundaries and consumes the entire record. Preserve unknown
record types, attribute bytes, length widths and padding. A rename and
an attribute-only edit produce distinct `O` artifacts and share the
same body ID if the body bytes are identical.

`M` represents a complete model manifest.

    u64 count  count * (bytes name  ID object)

Entries use strictly increasing names. Object IDs are nonzero and each
reconstructed `O` must have the exact manifest name. The manifest
contains `_GLOBAL` and all other named application records, including
hidden records. Exclude a recognized `_BRLCAD_HISTORY` archive. Exclude
file headers, free space and directory offsets.

`R` describes a revision and its change relative to a single parent.

    ID parent  ID model  i64 time  bytes label  bytes author
    u64 change_count  change_count * (bytes name  ID before  ID after)
    u64 rename_count  rename_count * (bytes old_name  bytes new_name)

A zero parent denotes the initial revision, with a full manifest and
no change or rename entries. Other revisions have at least one change.
Model is its nonzero `M` ID. Changes use
strictly increasing names. At least one of before and after is present,
and their IDs differ. A zero before means creation and a zero after
means deletion. Apply each before check against the parent manifest
before applying the after change. Hash the resulting manifest and
require it to match model. Rename hints are ordered by old name, refer
to changed names, and pair a deletion with a creation. Each endpoint can
occur once. Before and after records and their references remain the
authority for replay. A hint describes an edit and cannot change it.

Archive container
-----------------

The DB5 record uses the name `_BRLCAD_HISTORY`, the hidden flag, major
type 9 (binary uniform), minor type 4 (unsigned bytes) and an
uncompressed body. The body bytes begin with this eight-byte signature.

    42 52 4c 43 41 44 48 00

Recognize an archive only by its name, signature and DB5 wrapper.
Preserve a user object with a colliding name and refuse to enable
embedded history until the name is available. A recognized wrapper and
signature with unreadable metadata are handled as damaged history.

The pack header has the following fixed fields in order.

    u8[8] signature
    u16 major_version       (1)
    u16 minor_version       (0)
    u64 required_features   (0)
    u64 pack_length         (entire DB5 body)
    ID selected_revision
    ID selected_model
    u64 metadata_length
    u64 index_count

Metadata follows the header and consumes exactly metadata_length bytes.

    u64 boundary_count  boundary_count * ID revision
    u64 reference_count  reference_count * (bytes name  ID revision)
    u64 preference_count  preference_count * (ID parent  ID child)

Boundary entries name revisions with omitted parents. Such revisions
keep their original parent IDs and have materialized `M` artifacts.
Order those entries by revision ID, references by byte name and
preferences by parent ID, with no duplicates. Reference names are
checkpoint names. A preference selects a retained direct child for
Redo. All selected, referenced and preferred revisions must be present.

The index follows metadata. Each entry consists of u8 tag, ID artifact,
u64 offset and u64 length. Sort by tag byte and then by ID bytes, with no
duplicate keys. Offsets are relative to the signature and point into the
DB5 body. A 32-byte SHA-256 digest of the header, metadata and index
follows the index. Artifact payloads follow the digest in index order
and exactly fill the remainder of the body without gaps. Version 1.0
stores canonical payload bytes directly. A reader handles unknown
versions or required features without changing the archive or model.

Verify lengths and monotonic ranges against the enclosing DB5 field
before allocating tables or reading payloads. Verify the header and
index digest and hash each referenced payload before trusting it. A
full verification also walks all retained revision chains and content
references, rejecting missing artifacts, invalid names and cycles.
Require a stored `M` for the initial revision, each boundary and the
selected revision. No retained revision may be more than 64 parent
links from a stored `M`. Materialize other manifests through the
recorded changes. Intermediate manifests still have IDs even when
their payloads are only computed. A pruned revision's missing parent is
legal only at a declared boundary with a verified full manifest.
After selecting a new model, an embedded writer can omit the prior
selected manifest if all revisions still satisfy the replay bound.

The selected revision must name the selected model. Compare the live
DB5 named records with that model by factoring the records and hashing
the resulting manifest. A mismatch detects external edits. Keep the
archive self-contained so all retained revisions remain recoverable
when live objects change. Save archive and live model in the same DB5
publication. A history-free export excludes the recognized archive.

Workspace bootstrap and indexes
-------------------------------

The workspace stores canonical artifacts in an LMDB directory. Read
the `workspace` key in the unnamed database before opening any named
databases. Its fixed bootstrap value uses the following fields.

    u8[8] signature           (42 52 4c 43 41 44 57 00)
    u16 schema_major          (1)
    u16 schema_minor          (3)
    u64 required_features     (6 or 7)
    u16 artifact_encoding     (1)

Reject unrecognized schema versions, feature bits or artifact
encodings before interpreting the workspace data. The `head` key in
the unnamed database contains the selected revision ID, the selected
model ID and a u64 generation that starts at 1.

In schemas 1.0 through 1.3, the named `artifacts` database maps a
one-byte artifact tag and an ID to the canonical payload. The `directory` and
`references` databases use SHA-256 of the raw name as the key. The
value is the object or revision ID followed by the original name.
Compare the original name on lookup. A name conflict under the same
hash is an error. In `preferences`, a parent revision ID maps to its
preferred child ID. In `boundaries`, the key is the boundary revision
ID and the value is empty. Import verifies the copied archive and
directory in the transaction that publishes these tables and the
bootstrap.

The importing process reserves the canonical destination path until
its LMDB environment closes. It can open other workspaces during the
import. Readers in other processes require the committed bootstrap
before accepting the destination as a workspace.

Before the import transaction, creation synchronizes the new
workspace directory to persist the LMDB file entries, then synchronizes
its parent to persist the workspace entry. The durable LMDB commit
publishes the bootstrap after both synchronizations succeed. A reported
synchronization failure aborts creation and attempts to remove the
incomplete workspace.

Before switching the open document, GED compares the reopened snapshot's
revision ID, model ID and generation with the committed import. If
reopening fails or the head differs, GED keeps the source document open
and reports that the import was committed.

An open workspace tracks the identities of its LMDB data and lock
files. Additional handles must refer to the same files, and writes
check the identities before starting and before committing. Reader
retention locks must refer to the open data file. Move or replace a
workspace only after closing all its views. Its LMDB files are regular
files with one directory entry each.

Each artifact occupies one LMDB value and must fit the linked LMDB
library's per-value limit, at most 4 GiB minus one byte. A workspace
can exceed that size in total across its values.

Revision selection checks the exact checkpoint name first. Otherwise
it decodes a case-insensitive hexadecimal prefix and seeks to the first
possible revision key in `artifacts`. Two matching keys make a prefix
ambiguous. This also works for prefixes that end in half a byte and
uses the same keys in every workspace schema.

An edit compares its expected revision, model and generation with the
current head in the write transaction. It records the new artifacts,
checks the before and after model IDs, updates the directory, and
advances the generation together with the selected head. Checkout
reconstructs the target from the nearest stored manifest when needed,
advances the generation on a selection change, and records the redo
preference when moving between a parent and child.
Creating or moving a mark compares the same generation and publishes
the new name or target with an advanced generation.

Schema 1.2 and later require sparse manifests (feature bit 1). The `directory`
table materializes the selected model. A stored `M` is required for
the initial revision and each retention boundary. Other revisions may
replay at most 64 parent links to a stored `M`. Writers materialize
periodic snapshots within that bound. Checkout updates the selected
directory without requiring a new artifact. For a portable export or
archive verification, reconstruct the selected `M` when it is absent
from `artifacts` and verify its canonical ID.

Schema 1.3 requires the revision-child index (feature bit 2). Its
`children` table has one empty value per retained parent-child edge.
The key concatenates the parent's 32-byte revision ID and the child's
32-byte revision ID. The initial revision and retention boundaries
have no indexed parent. Insert edges in the same transaction as a new
revision. Remove edges to expired children and new retention boundaries
in the prune transaction. Verify the index against all retained revision
records. A status query reads children with a range scan on the
selected revision ID. Earlier schemas read the revision graph.

An optional `last_export` key in the unnamed database holds the ID of
the last successfully exported revision recorded by a writable
workspace handle. The optional `last_export_observation` key contains
the same 32-byte revision ID followed by the big-endian unsigned
64-bit export time in Unix seconds. Readers use the time only when the
IDs agree. Both keys are written in one transaction without advancing
the modeling generation. Earlier readers can still read `last_export`.

Pruning publishes retained artifacts, new boundary snapshots, updated
redo preferences and the advanced generation together. Unchanged
revisions keep their original IDs and parents. A retained revision
with an expired parent is a boundary. Its model is materialized, and
both sides of its recorded changes remain available for verification.

On systems with local advisory file locks, a native database reader
registers its selected revision by locking the matching hexadecimal
name in `history-pins`. A lock on `data.mdb` coordinates registration
and pruning. A reader unable to register keeps a shared lock on that
file for its lifetime, which postpones pruning. The operating system
releases reader locks after process exit. These files are local
coordination state and are omitted from exports and new workspace
copies.

Schema 1.1 requires the reader-pin protocol (feature bit 0). Schemas
1.2 and 1.3 set that bit when the store uses the same protocol. Schema 1.0
has required features zero and supports inspection and ordinary
editing. Copying a 1.0, 1.1 or 1.2 workspace creates a verified 1.3
workspace with the same retained revisions and selected model.
Pruning is available on the copied workspace when reader locks
are present. The source stays available throughout the migration.

A plain DB5 export reads each record by immutable object ID from the
pinned model, then closes the read transaction before writing the
record. The destination is synchronized with no workspace read
transaction held. A history-preserving export holds a consistent read
transaction while streaming the model and retained archive, then
releases it before synchronizing or reopening the staged DB5. Recovery
exports for stale workspace edits follow the same transaction lifetime.
